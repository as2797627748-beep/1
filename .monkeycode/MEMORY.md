# 用户指令记忆

本文件记录了用户的指令、偏好和教导，用于在未来的交互中提供参考。

## 格式

### 用户指令条目
用户指令条目应遵循以下格式：

[用户指令摘要]
- Date: [YYYY-MM-DD]
- Context: [提及的场景或时间]
- Instructions:
  - [用户教导或指示的内容，逐行描述]

### 项目知识条目
Agent 在任务执行过程中发现的条目应遵循以下格式：

[项目知识摘要]
- Date: [YYYY-MM-DD]
- Context: Agent 在执行 [具体任务描述] 时发现
- Category: [代码结构|代码模式|代码生成|构建方法|测试方法|依赖关系|环境配置]
- Instructions:
  - [具体的知识点，逐行描述]

## 去重策略
- 添加新条目前，检查是否存在相似或相同的指令
- 若发现重复，跳过新条目或与已有条目合并
- 合并时，更新上下文或日期信息
- 这有助于避免冗余条目，保持记忆文件整洁

[部署用词偏好]
- Date: 2026-04-21
- Context: 用户表示不希望继续使用“幂等部署”这种不直白的表述
- Instructions:
  - 部署能力相关命名统一优先使用 `稳定部署`
  - 后续少用“幂等部署”这类偏工程术语
  - 涉及同一含义时，优先改用“可重复部署”“重复执行也安全的部署”或类似更直白的中文表达
  - 避免使用“收敛”等偏数学或偏算法术语描述部署能力
  - 部署相关命名需要自然、正式，不要太口语化，也不要太学术化
  - 涉及准备阶段的区块命名统一使用 `部署准备`，不要写成 `部署准备项`
  - 避免使用 `闸门` 这类偏工程黑话，优先改用 `检查`、`要求`、`当前状态` 这类直白说法

[全局文案表达要求]
- Date: 2026-04-21
- Context: 用户进一步明确界面与回复的整体表达风格
- Instructions:
  - 任何面向用户的文案都不要出现工程化黑话
  - 表达必须直白易懂，但不要像机翻或生硬直译
  - 整体风格要产品化、高端、轻奢、中文化
  - 优先使用自然、克制、简洁的中文，不堆术语，不用生硬英文式表达
  - `复验`、`回退` 这类简单、通用、自然的中文表达可以保留
  - `重点确认`、`恢复版本` 这类一看就懂、足够通用、读起来顺的表达也可以保留
  - 需要避免的是生硬、不自然、偏术语堆砌的表达，如 `闸门` 这类让人出戏的说法
  - `版本记录` 这类专业且简短的表达可以保留，不必为了变化而改得更花
